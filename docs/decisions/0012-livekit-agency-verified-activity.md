# ADR 0012: LiveKit rooms, agency workflows and verified activity

Status: implemented for independent review; authorized by owner request dated 2026-11-25. Baseline main 645c75c. Wallet independent review remains pending. No production acceptance, provisioned server, infrastructure change or financial approval follows.

## Boundaries and dependencies

The explicit batch request supersedes earlier LiveKit/agency implementation deferrals only within its backend scope. `internal/modules/live` owns room policy and orchestrates provider intent; its PostgreSQL adapter composes Access's existing mutation-boundary transaction. Existing `agency` owns the pure calendar/interval calculator; Wallet remains the only financial writer. Identity, premium entitlements, staff scope, agency membership and room role remain separate. Redis is unused for authority or coordination.

Use the official Go server SDK v2.16.7 and its protocol dependency v1.48.1-0.20260624204523-bd5703442db6, compatible with the existing Go 1.26.3 module. The inspected latest v2.20.1 and v2.19.0 require Go >=1.26.8; no toolchain upgrade is introduced. The SDK brings media/protobuf dependencies even though this application never opens a media connection. See [official server SDK](https://github.com/livekit/server-sdk-go), [room APIs](https://docs.livekit.io/reference/other/roomservice-api/) and [webhook verification](https://docs.livekit.io/intro/basics/rooms-participants-tracks/webhooks-events/). Local adapter tests exercise its exact pinned JWT/checksum verifier and controlled HTTP endpoint, not a live SFU.

## Association and permissions policy

Agency ID equals its immutable owner account ID to preserve existing Wallet association/commission references. No ownership transfer is specified or implemented. Agency profiles are pending until scoped staff activates them; pending/rejected/restricted agencies cannot approve hosts or create qualifying activity. Owner or explicitly delegated managers manage that agency's applications; self-approval is denied; `agency.hosts.manage` supports global host decisions/classification. No manager can appoint managers; owner or `agencies.manage` does that. Managers do not acquire account/staff/financial authority.

One active host association per account is enforced by the existing unique index/history trigger and shared transaction lock. A classification change closes the prior row and creates a new historical association. Association writes are centralized in the transaction-bound Agency PostgreSQL writer, reused by new workflows and the existing Wallet operator API without changing its authorization/effective-date/financial audit behavior. Existing Wallet operator association APIs remain compatible; an association without an active agency profile cannot create/publish qualifying media. Membership requests are host applications, not a second parallel membership classification. Leaving closes the association immediately. Historical evidence is retained.

No host-type inheritance is assumed. All four host-type/room-type combinations default to false until explicitly configured. Immutable CAS-published admin live policies may override the validated environment defaults within configured hard capacity/seat ceilings. Each authorization boundary reads the current policy. Publishing invalidates open qualifying evidence and queues provider corrections for up to 500 current publishers, failing atomically above that supported batch bound. Activity thresholds/timezone are still published exclusively through existing immutable Wallet activity policies. No commercial rate/tax/provider is invented.

Hosts create rooms and control roles/closure. Co-hosts and moderators can moderate audience/seat users, but cannot alter host authority or moderate peer co-hosts/moderators. Only owner/scoped room staff appoint room roles. Audience joins are allowed for active authenticated accounts; publishing/seat acceptance requires a compatible active agency-host association. This is the restrictive supported policy for unspecified independent-host eligibility. A room moderator has no implicit media publishing grant. Audio publication allows microphone only; video permits microphone/camera only. User tokens grant no RoomAdmin, data publishing, metadata editing, screen publishing, provisioning or credential access. JWT TTL defaults to 60 seconds, bounded by two minutes.

## Durable effects and operational bounds

Room identity and live-session identity differ. State is opening -> open -> closing -> closed; closed sessions never reopen. One current room per owner. PostgreSQL owns memberships, capacity reservations, bans, roles, invitations and unique occupied seats. Room kicks deny readmission until explicit host/admin unban. Mutations use actor/operation/key fingerprints and persist result plus audit plus provider intent atomically.

Ordered room operations are claimed with a 30-second durable lease; remote calls use a <=5-second context and no database transaction/connection is retained across them. Create/delete/participant updates are idempotent desired-state operations. A provider success followed by local commit failure remains replayable. Local privilege revocation cuts off activity immediately, while media convergence is explicitly pending until provider correction. Responses never equate accepted intent with applied media state. Claims stop at 100 attempts; an explicit scoped/audited reconciliation resets at most one exhausted operation for another bounded retry cycle. Admin room detail exposes a bounded pending-operation preview and exhaustion/lease metadata. No background goroutine/worker is installed. Request retries, verified webhook delivery retries and explicitly scoped room reconciliation advance one ordered operation each; pending backlog returns pending/503 as appropriate. A cancelled request can leave durable pending work, never a fabricated success.

The SDK room client uses its own http.Client with the standard shared transport. An adapter semaphore bounds concurrent calls to eight per process; contexts bound queueing and provider calls. No SDK media room, local authoritative cache, goroutine loop or sticky session is created. Standard transport idle sockets expire under its defaults; the adapter does not close global transport connections belonging to unrelated clients. HTTP/process draining and PostgreSQL/Redis close behavior retain the existing lifecycle.

Goose's session-lock acquisition budget increases from 10 to 60 seconds, still bounded by the existing two-minute CLI context: additive migrations exposed lock-acquisition timeout during the existing concurrent-upgrade test on the remote isolated database. The full concurrent success assertion is retained. Test scenario budget increases from 90 to 180 seconds to cover two added migrations. This changes operator contention wait, not runtime pool/security locking.

Existing connections must reconnect after seat/role/classification/policy changes to establish new qualifying evidence. An audience connection is never retroactively upgraded to qualifying time; prior qualifying time stops at its invalidation cutoff. This conservative boundary can undercount time and needs controlled provider/client E2E verification.

## Restriction and provider recovery hardening

Migration 7 persists immutable server-clock account-restriction ceilings. Identity remains the account/session write owner; a Live-owned transaction adapter records the ceiling, leaves memberships/seats and queues provider removals in that same transaction. No provider call occurs under those locks. Source queries clip at the first restriction within an interval. Unrestrict never restores a session or credits the blocked portion of an old connection. New verified connections after fresh authentication may qualify normally. Ordinary APIs enforce at most 50 active room memberships per account. The new active-member index supports room inspection/closure without scanning historical inactive members.

Provider snapshots distinguish an empty room from a missing room. Verified absence closes local admission; unexpected recreation with a different provider SID queues provider deletion without establishing new activity. Reconciliation batches missing-SID abandonment rather than issuing a database update per participant. The current implementation deliberately has no automatic continuous-connection billing checkpoint worker; completed verified evidence is required. Physical provider removal is pending until applied and must not be inferred from account-status success alone.
