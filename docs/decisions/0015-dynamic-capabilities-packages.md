# ADR 0015: one capability resolver, global moderation and configurable packages

Status: owner-authorized consolidated backend batch, 2026-11-25; implementation/review pending. Baseline e94b765. No independent Wallet/Live approval is inferred.

## Authority

Extend Access's existing PostgreSQL security transaction and advisory lock. Access.Resolve is the single effective-capability engine for protected App Owner, assigned staff permissions, current room-policy roles, safe active-package powers, and direct global/room overrides. Role/package display names never authorize. Ordinary grants are a union; any applicable direct denial wins. Installation/account restrictions are still checked by Identity and cannot be purchased away. Protected owner authority remains outside editable role/override configuration; normal override APIs cannot target it. Financial critical operations retain their existing protected-owner controls. Legacy staff-permission projections omit implicit participation/purchase defaults; the effective-powers API exposes the full resolver result. Authenticated financial retries retrieve an already committed outcome before evaluating new-purchase denial or current package activation. New purchases still require current authority and configuration.

The executable capability catalog is fixed by backend code and mirrored in a read-only database catalog. Administrators select supported verbs, never arbitrary executable actions. Room policy is append-only with predecessor CAS and audit. Mandatory resource/live restrictions are included in the same resolver, and direct entry denials invoke Live-owned participation cuts in the audited transaction. Room policies may grant only room.* actions, never global bans or financial/staff delegation. Direct overrides are protected-owner administered, expire within 366 days, and remain scoped. Existing staff role administration is reused; a new explicit preset-creation API supplies Global Moderator defaults with an editable name. Names do not trigger automatic defaults or implicit power.

Global Moderator is assigned staff authority across rooms, distinct from an existing room moderator membership. Defaults include public/private entry, hidden entry, participant kick/mute/seat removal, self-call/seat join/leave and global-live-ban administration. Additional capabilities require explicit staff assignment. Private/hidden entry is a protected staff capability, not purchasable. Private-entry provenance is server-owned so revoked staff access cannot survive as ordinary membership. Room ownership/classification does not imply global staff status. Ordinary room owners can be moderated by authorized global staff; protected App Owners cannot be targeted. Room ownership/host role cannot be transferred or removed through ordinary role assignment.

## Hidden entry and provider boundary

Use the pinned official SDK's VideoGrant.Hidden and ParticipantPermission.Hidden. Hidden membership remains an authenticated/audited account identity and is filtered only from ordinary participant projections, not authorized operations/admin projections. Hidden participants receive explicit publish/data/metadata/admin denials; taking a call requires a visible membership. Audio uses the existing unique seat index. Video self-calls use trusted self_seated state and a unique slot; the current live seat policy bounds total existing host/co-host/call publishers, capped by room capacity. Agency host classifications still independently determine compatible verified activity; a staff/package power does not create an agency association or fabricate qualifying time.

Official references: [participants](https://docs.livekit.io/intro/basics/rooms-participants-tracks/participants/), [tokens and grants](https://docs.livekit.io/frontends/reference/tokens-grants/), [room service API](https://docs.livekit.io/reference/other/roomservice-api/). SDK claim/update tests are controlled tests. Actual SFU/mobile behavior, track/audio side channels and self-hosted reconnect/revocation remain NOT TESTED. No claim that hidden means anonymous, inaudible or invisible through every signal. Mobile tokens never receive roomAdmin.

Global live bans are independent records plus immutable audit/idempotency outcomes. They block live entry/token use, cut open qualifying evidence at a server timestamp and enqueue removals for the bounded current memberships, without suspending accounts or restricting installations. Completed activity/history is retained. Backend permission revocation is checked on every action across instances, token issuance and privileged participant admission. A newly delivered signed join event cannot create qualifying presence for a now-revoked hidden/self-call/private-entry grant. Historical signed left/completed evidence retains its original handling; provider convergence is asynchronous and can remain pending during outage.

## Packages and accounting

Package codes are stable, names arbitrary, and current configuration versions immutable. Current active configuration supplies all active subscribers' powers/assets/listing priority. Already purchased price/version and subscription periods are immutable. Multiple distinct packages can coexist; net powers are the safe union and listing priority is the maximum, never a sum. Expired/revoked/inactive packages contribute nothing. Supported purchasable powers are public room entry, self-seat/call join/leave, badge and entrance metadata; no hidden/private entry, global moderation, bans, staff delegation, owner or ledger authority. Assets reference ready, administratively managed image assets; immutable package history protects those references from garbage collection. Rendering/animation/frontends are outside this batch.

Owner confirmed that the **entire diamond price is platform profit, without VAT or agency commission**, and requested a separate profit table. Wallet remains the only financial transaction/write owner. Its new purchase operation uses the same spendable account, checked integer posting, conserved ledger and actor/operation idempotency. A narrow package-owned transaction adapter creates the entitlement/purchase metadata; the Wallet posting function credits platform:packages and appends package_profit atomically. Profit is an immutable journal, not a second spendable wallet. The prior financial posting body is preserved as a private routine; runtime cannot bypass the new Wallet entry point. No fiat payment, external settlement or automatic refund on entitlement revocation is introduced.

Owner additionally confirmed: buying an already active package **extends its duration: a new paid period starts when the old period ends**. New purchases append after the last non-revoked, unexpired same-package period (including queued periods); existing periods are not modified. Distinct packages have independent timelines. A prior-key retry returns the same operation and period. Current active entitlements exclude scheduled future periods; purchase history exposes immutable starts_at/expires_at. Revoking a period does not rewrite or reflow later paid periods. Missing/inactive price or accounting configuration still fails closed.

## Discovery and recovery

The actual mobile /rooms query applies open/public visibility, an active host membership/account, platform/room bans and entry denials before a single SQL max-priority join. Only the owning host's current active package terms contribute. Ordering is priority descending, room ID ascending. Results are bounded to 50 plus one, with indexed joins and no per-row SQL/remote calls or Go sorting. SQL aggregation can still cost more with many open rooms; production load performance is unmeasured.

Cursors reference an actor-bound database snapshot/revision, valid at most 30 seconds and no later than a relevant host term start/expiry or caller entry-denial expiry. Ranking uses one captured server time and rechecks revision/deadline after the query. Expired/changed cursors return LIVE_LIST_RESTART_REQUIRED (409). Relevant room/host/package/ban changes bump revision; ordinary mute/seat updates and audience-only subscriptions do not invalidate ordering. Mutable snapshot storage is scheduling metadata, not authority; bounded expiry cleanup runs on first-page requests.

A bounded worker sweeps ten hidden/self-call/private-entry memberships per page and commits revocations before provider I/O. Provider retries use bounded jittered backoff; local authority recovery can continue while remote delivery backs off. Existing Live operation 100-attempt limits and explicit audited recovery are preserved. Added lease-token fencing prevents a stale provider attempt from completing/retrying another worker's reclaimed lease. The worker also drains bounded oldest pending operations and joins shutdown; no unbounded queue, per-recipient remote call in a financial transaction, or exactly-once claim is introduced.

Migrations 10–11 are additive and guarded on rollback. New migration bodies are Goose statement groups inside their existing transactions to avoid one network round trip per DDL statement; historical migrations are unchanged. Production application rollout/backup/restore/rollback and real providers require separate acceptance and authorization.
