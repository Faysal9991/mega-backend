## Accounting and transaction boundary

A user has exactly one available diamond account (`user:<identity-id>`), plus a non-spendable held account (`held:<identity-id>`). Both represent the same DIAMOND unit. Agency commissions credit the agency beneficiary's ordinary available account, not a separate spendable agency currency. Platform fees, gift revenue and tax allocations have named non-spendable platform accounts. Issuance is an explicit negative-supply contra-account: owner adjustment credits issue supply, compensating debits retire it. No public purchase, reward or commission credit bypass exists without a separately verified operation adapter.

All amounts/postings are checked int64 whole diamonds. Sum(postings)=0 for each operation; fees and distributions never silently issue/burn. A SECURITY DEFINER, fixed-search-path posting function is the sole runtime writer of balances and ledger entries; runtime cannot directly update balances or mutate ledger history. It locks distinct accounts in deterministic ID order and enforces balance range, nonnegative available/held/platform balances and per-operation conservation. A deferred operation constraint rejects missing/unbalanced postings at commit. Ledger, immutable operation/fingerprint/policy snapshot, reservations, transition event and audit commit together. Transaction/commit errors are never retried automatically; clients reconcile by their actor/operation/idempotency reference. State is PostgreSQL-only; Redis never authorizes.

Identity owns authentication/restrictions; Wallet owns accounting writes through narrow transaction-bound initialization. Existing accounts are backfilled with zero wallets; signup creates user+held accounts atomically. No existing profile, Google binding or session data is reset. Financial commands reuse the existing advisory security lock and authoritative session/permission checks; funds are posted under sorted account locks. No provider/cache network I/O occurs inside a financial transaction. The current conservative global lock remains a documented contention risk, not a throughput claim.

## Policies and disabled defaults

No policy is active by default. Policies are immutable versions with effective_at, scope, prior-publication concurrency token (independent of effective-date order), audit reason and actor/correlation. Only protected owner authority plus the explicit economy permission may configure policies, classifications or issuance adjustments. Review and inspection have separate assignable permissions; users.profile.update never permits financial actions.

Transfer policies explicitly configure enabled, positive min/max, fixed and basis-point fee (explicit ceil rounding), and optional UTC calendar daily/monthly caps. Recipient account must be active, existing and distinct. Idempotency binds actor, operation kind and canonical request fingerprint; retry returns the original result even after a new policy becomes effective.

Gift policies explicitly configure a bounded server-side gift catalog, agency/non_agency scope, host/agency/platform/tax basis points summing to 10000, inclusive_diamonds VAT treatment and largest_remainder allocation with deterministic host/agency/platform/tax tie order. Unsupported fiat/exclusive VAT or absent scope/catalog/distribution remains configuration-required. No percentages are seeded. Policy/catalog snapshots are immutable. Agency recipient comes from the effective authoritative association; unassociated hosts require an explicit non_agency policy. This financial layer has no LiveKit/session-presence or animation integration; live-room membership enforcement remains a future adapter requirement.

Withdrawal policies explicitly enable diamond-only review reservations, positive min/max/fees and optional UTC caps. Without an explicit review_only policy requests are configuration-required: no provider or conversion is configured. Pending requests reserve amount+fee from available into held. Owner cancellation is pending-only; authorized review can approve pending, or reject pending/approved before any payout. Approval retains funds and explicitly reports settlement unavailable, never paid/settled. Rejection/cancellation release the full reservation; no fee is captured and no supply is burned. Transitions are actor/key/fingerprint idempotent with immutable events/audit. Actual external payout/confirmation/capture/refund remains disabled.

Agency host activity is an additional requirement. Classification is audio_host/video_host, separate from permissions/status/premium/auth. Effective associations retain history. Activity policies must explicitly select timezone, previous_completed_calendar_month period and thresholds (owner-approved initial activity thresholds 15 distinct days / 120 verified minutes per day, configurable). Previous completed calendar month is proposed, not activated by default. Trusted injected session data is deduplicated, overlaps merged, clipped/split at configured month/day boundaries. Runtime trusted collection is unavailable, so agency-host withdrawal fails closed. Tests use synthetic verified fixtures. No client activity claims are accepted.

Lists use immutable hex-ID keysets, bounded maximum 50, no unbounded counts/N+1; history lists omit per-operation policy snapshots; detail and applicable-policy summary projections include the versioned policy. ## Version selection, limits and provenance details

Publication revision is a database identity sequence. A write must supply the latest published version ID as previous_policy_id; active selection orders effective_at then revision. Future staging does not prevent an immediate correction/disable. An already-scheduled future version still becomes active at its own time unless superseded by an explicit replacement at that effective timestamp; operators must inspect pending policies when responding to an incident. Completed operations never change their saved policy. No default fees/rates/period caps are inserted.

Configured daily/monthly caps count accepted principal diamonds (excluding fees) in UTC calendar windows using the PostgreSQL clock. Rejected/cancelled withdrawals retain their original accepted reservation usage; release does not erase immutable period usage or enable reservation cycling. These semantics are part of the reviewed policy contract, not inferred from legacy behavior. A zero explicit cap means no cap for that calendar window; positive per-operation min/max is always required. Agency activity has its separately required configured business timezone and previous completed calendar month. Association changes close an open interval and append a new row; overlapping/rewritten closed history is rejected. No historical agency-transition activity-proration rule has been invented; real trusted collection and any additional commercial timing rules require independent review before runtime activation.

Every entry joins an immutable operation with source kind, actor, counterparty, reference/catalog gift ID and relevant policy snapshot. Gifts credit host/agency available wallets plus named platform/tax accounts; non-agency scope requires agency_bps=0. Purchases/rewards without a verified producer adapter remain unavailable; the owner-only adjustment command is explicit issuance/retirement with reason/reference, not a payment-provider bypass. All posting accounts use the same diamond unit. No fiat conversion or tax payment is inferred from a diamond tax allocation.

The ordinary operation detail filters postings to the authenticated user's own available/held accounts; admin inspection requires wallet.operations.read. Historical association and policy records support reconstruction without returning another user's ledger through ordinary APIs. Reconciliation (`walletsql.Reconcile`) compares each account balance with the numeric sum of its immutable postings and returns at most 100 mismatches. Integration acceptance requires zero mismatches. The immutable publication/command/outcome records and safe audit metadata retain old/new policy IDs and operation correlations; no passwords, tokens or payout-bank data are stored in this scope.

Migration 4 adds eight finance tables, a bounded posting function, a deferred conservation/audit trigger and an association history guard, plus six permission catalog entries. Runtime cannot insert ledger entries, update balances or mutate operation/policy/command history. System-account IDs/kinds are fixed. Identity may invoke only the Wallet-owned zero-account initializer during signup; the root Identity repository cannot create a Google account outside a transaction. API startup checks both Identity/Profile/Access artifacts and Wallet artifacts within one existing startup deadline; no runtime DDL. Down refuses populated financial operations; production data recovery is separately reviewed and never automated here.

All configured effective timestamps and association dates are normalized to UTC microsecond storage precision without mutating caller objects. Activity collection uses the PostgreSQL clock and is rechecked against the current policy, association and completed-month bounds before reservation; a month rollover or changed policy cannot authorize a stale activity result. Ordinary HTTP financial credentials reject duplicate identity/bearer headers; the existing Identity/Access session checks remain authoritative. Publication CAS and active-effective selection have separate derived indexes; unused actor/target/review-state indexes are not added. Reconciliation is an explicit operator/test scan, not an automatic query on normal wallet requests.
