# Gifting, media and notification delivery

Status: implemented for independent review, owner-authorized at main c749cec. Wallet and LiveKit independent reviews remain pending. ADR 0014 records decisions and SDK evidence. No legacy source/data bridge or production/provider provisioning is included.

## Module and write ownership

`delivery` defines pure contracts, validation, cryptography, templates and image processing. `delivery/postgres` implements application workflows through the existing Access-authorized transaction; its SQL is generated with sqlc. HTTP depends on pure delivery contracts. Provider adapters are separate objectstore/fcm/roomdata packages; the API imports the S3 adapter, while Firebase SDK initialization belongs only to `cmd/worker`. Wallet is the only accounting writer; Live validates room business authority; Profiles owns avatar mutation. Small transaction-bound intents/bindings adapters let Identity/Live enqueue notifications and unbind devices without circular imports or provider calls under locks.

All new mutable HTTP JSON uses an opt-in canonical snake_case decoder. Existing decoder behavior is retained for older contracts. Body cap is 32 KiB, list limits 1–50 (default 20), idempotency keys actor/operation scoped, privileged changes atomically audited. See delivery.openapi.json and executable fixtures. Catalog paging uses display_order/id over the current catalog, so concurrent edits can change traversal; histories use immutable ID order. Null optional catalog descriptions/asset references clear them; upload target omitted/null defaults to the authenticated actor. Required policy predecessor, attachment predecessor and preference booleans reject null/omission.

## Catalog and financial boundary

A stable gift ID/code points to an immutable version containing presentation, positive int64 price, active state, category, display order and approved thumbnail/allowlisted animation references. Updates use previous_version_id CAS; creation time remains stable and updated_at follows the version. Category/order changes and deactivation publish a new version. There is no seeded price, commission, VAT rate or active recipient policy.

Live sends require explicit active_publishers recipient policy, an open matching immutable room/session, authenticated active sender, current active memberships, verified open provider-presence evidence for both, and a currently compatible publishing recipient/agency. Recipient/room authority resolves before financial distribution lookup. These checks use PostgreSQL evidence, not synchronous provider calls; missing disconnect/reconciliation evidence can lag physical presence, a real-provider acceptance gate. Suspended accounts, audience recipients, mismatched/closed sessions and missing policy fail closed.

Wallet retains existing agency/non_agency distribution policy, checked multiplication/addition, largest-remainder allocation, inclusive-diamond VAT snapshots, deterministic locks, balanced posting and idempotency. Financial policy JSON remains equal to its immutable policy row. The live gift stores an immutable catalog version reference in the same transaction as Wallet posting and a room event/outbox intent. Older non-room Wallet gifting retains its policy-catalog contract and does not emit room animations; it cannot fabricate a live-room gift event. Empty optional room/session fields are omitted from internal canonical JSON so pre-c749cec non-room idempotency fingerprints remain valid (golden regression).

The send response states financial_status=committed and delivery_status=not_confirmed. Retry returns the earlier financial outcome before current catalog/room revalidation, including after deactivation/closure. History exposes independent delivery state; delivered means the provider accepted the request, never that every participant displayed it. Event type room.gift.v1 includes operation/event ID, room/session, bounded public identities, gift/version, quantity, committed diamonds, animation reference and UTC time. Clients deduplicate event IDs; neither animation nor push proves settlement.

## Media lifecycle and privacy

Create intent -> five-minute exact-key/length/MIME/SHA-256/private-ACL presigned PUT -> ten-minute completion window -> claim two-minute processing lease -> HEAD + ETag-conditioned GET -> actual JPEG/PNG validation -> metadata-free PNG and thumbnail -> approved state -> optional attachment. Remote calls and decoding occur without transactions. Completion rechecks actor/scopes before final commit; repeat ready completion returns the stored result. Temporary provider failure leaves pending, malformed data becomes failed, and concurrent claims conflict until lease expiry.

Inputs are at most 2 MiB, each dimension 4096 and decoded pixels 4,000,000. Main variant fits 1024, thumbnail 256, preserving aspect ratio; PNG output is capped at 8 MiB. At most two processors per API process; admission returns 429. No binaries/base64 images enter PostgreSQL. Supported purposes: own avatar, administrative agency_logo and gift_thumbnail. Banner is unsupported by the current Profile. Agency logo attachment additionally requires agencies.manage. Avatar compare-and-swap attachment updates the existing Profile-owned avatar_url. GET attachment exposes the current replacement token; avatar links are self-only and agency-logo links expose approved public URLs.

Pending/original keys are private server-generated keys. Only processed images use approved prefixes; originals never receive public URLs. Public URL configuration does not configure a bucket/CDN: before use, verify private bucket permissions, signed private ACL/checksum support, a dedicated HTTPS media origin that serves only approved prefixes, CORS and environment separation. Garage does not need to exist for build/unit/API startup with media disabled. External gift-animation HTTPS references require configured exact host allowlists and approved extensions; these are administrative references, not byte-verified animation uploads or a supplied client renderer.

An owner has at most 100 retained active assets / 200 MiB declared input quota. GC intent starts 24 hours after creation; replacing an avatar schedules old-asset GC after 24 hours. Under the existing security lock, GC checks both attachments and immutable catalog-version references before retirement. Retiring assets cannot attach; only then does remote deletion happen, followed by deleted metadata state. Referenced variants remain, while expired originals can be deleted. Partial output keys are deterministic and cleaned on unreferenced retirement. Quota excludes deleted metadata; retaining historical gift references deliberately retains their variants.

## Push binding and safe payloads

Register a token on the authenticated installation/session only, with Android/iOS platform. Tokens are AES-GCM encrypted with installation AAD, hashed for uniqueness, never returned or logged. Duplicate same-binding registration preserves revision; rotation/account switch uses a new revision. There are at most ten registered installations per account. Session creation clears only the authenticated account's own prior installation binding; pruning removes revoked bindings for that account; logout, logout-all, restrictions and installation bans unbind transactionally. Refresh preserves session identity. Existing session/identity authorization remains unchanged.

Five supported kinds: gift_received, agency_decision, account_event, room_invitation and admin_announcement. Preferences explicitly opt in, initially all false. Producers are committed live gifts, agency decisions, new sessions/revocations and seat invitations. Revocation records history but cannot notify through bindings it invalidated; other still-active installations can receive new-session alerts. Fixed public templates and event IDs carry no balances, contacts, credentials or tokens. Announcements select maintenance/service_update/community_update, target an explicit maximum 100 accounts, insert in a bounded batch and require scoped audit. No freeform private payload or global broadcast exists.

Fanout uses known notification IDs and at most ten bindings/account, never a global token scan. Before each send, recheck account/installation/session status, current token revision and preferences. Unregistered-token cleanup compares revision so it cannot remove a rotated token. Already in-flight/accepted pushes cannot be recalled on a concurrent logout. Preferences/token changes affect future dispatch, not history. Expiry cleanup uses an indexed server expiry (capped by family expiry and 60 days), max 100 rows per maintenance pass.

FCM uses official Firebase Admin SDK. Only bounded service-account JSON with an approved Google token endpoint is loaded; no ADC/external-account discovery, implicit FIREBASE_CONFIG, or SDK debug payload logging. OAuth HTTP is bounded to five seconds and asynchronous credential refresh disabled. SDK send contexts are five seconds. Invalid registration removes only its matching revision; invalid argument/project/APNs credential rejection is permanent without purging unrelated registrations; transient/quota/network failures retry.

## Dispatcher lifecycle and recovery

Build/run `go run ./cmd/worker` with the same isolated/environment DB, encryption key and optional provider configuration as API. Do not run this against production without the separate deployment approval. API has no dispatcher goroutine. The worker owns 1–4 joined workers plus one bounded maintenance loop. Each worker owns one claim, no in-memory durable queue, a 250ms admission tick and a one-second idle/error wait. Fixed worker/request admission provides backpressure; PostgreSQL durable backlog and immutable histories require disk/backlog monitoring and reviewed retention before production.

Claims use SKIP LOCKED, a random fencing lease and 60-second expiry; processing contexts are 30 seconds, provider calls five seconds. Acknowledgments match lease ID and running state; stale workers cannot overwrite a newer claim. Retries use jittered exponential delay capped at five minutes, max ten attempts. Crashed last-attempt leases become failed in bounded maintenance. Explicit deliveries.retry requires audit/idempotency and failed state; it republishes intent without any money posting. Poison/permanent failures remain visible. Media, gift and push topics whose providers are disabled are not claimed. Provider errors never undo committed money. Worker cancellation joins all owned goroutines and bounded cleanup before pool close; SDK/shared idle sockets are not globally closed.

Real Garage/S3, FCM device delivery and LiveKit room-data E2E remain NOT TESTED. No VPS throughput/p95/p99/CPU/RSS or production capacity guarantee is inferred from deterministic tests or local image microbenchmarks. Global security locking remains a throughput limitation. Next gate: independent review, explicit production policies/credentials/privacy/retention configuration, controlled provider E2E and production-like operational/load validation.

Account-switch security boundary: another account's active push binding survives a login that merely reuses its resettable installation ID. Registration conflicts unless the prior account logged out/binding became inactive, or previous_access_token proves the exact prior bound session on that installation. Both account sessions are checked under the same lock; the switch is audited atomically and rolls back on audit failure. Proof is never persisted, logged, returned or included in outbox payloads. Token-hash clashes across other installations fail closed; a push token is not ownership proof. An incomplete client switch has not transferred notification ownership; clients remove the old binding/log out or complete explicit two-session consent before treating push ownership as switched.
